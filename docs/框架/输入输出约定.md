可以把它们理解成“考题、标准答案、公证材料、生产过程录像、学生答卷”。

```text
输入 fixture
   ├── FreeCADCmd 运行 ──> *.freecad.json
   │                         ├── public/provenance ──> *.freecad.ledger.json
   │                         └── producer 过程 ──────> *.freecad.producer-trace.json
   │
   └── CAD Core 运行 ──> *.cad-core.json

检查 A：freecad.json <──> ledger.json     标准答案是否可信
检查 B：freecad.json <──> cad-core.json   CAD Core 是否答对
检查 C：producer trace 的 scope/checkpoint     CAD Core 最早从哪里开始不同
```

具体区别如下。

### `fixtures/<phase>/<case>.json`

这是“考题”，也就是输入模型、参数、引用和旧的 `topoNamingState`。

FreeCADCmd 和 CAD Core 理论上都应该读取同一份输入。

### `expected/<case>.freecad.json`

这是“标准答案”。

它来自 FreeCADCmd/native oracle，但不是 FreeCAD 内部所有数据的原样倾倒，而是经过 collector 裁剪后的公共协议结果，例如：

- `results`
- `diagnostics`
- `elementReferenceUpdates`
- 对外发布的 `topoNamingState`

CAD Core 真正需要对齐的是这份公共答案。

### `expected/<case>.freecad.ledger.json`

这是“标准答案的取证录像和公证材料”。

它记录：

- 谁生成的：FreeCADCmd、FreeCAD/OCCT 版本
- 使用了哪个输入：`inputHash`
- 对应哪份标准答案：`expectedPayloadHash`
- 原始拓扑对象和映射证据
- 引用解析事件
- 哪些对象被发布、哪些被裁剪
- 输入引用是否真的在 FreeCAD 中解析成功
- round-trip 是否通过

它的作用是防止出现这种问题：

> 某个 `.freecad.json` 看起来像 FreeCAD 结果，但实际上是手工编的、从旧 expected 反推的，或者引用根本没在 FreeCAD 中解析成功。

CAD Core 不需要输出一份 ledger，也不需要逐字段对齐 ledger。ledger 只是证明 `.freecad.json` 这个标准答案可信。

### `expected/<case>.freecad.producer-trace.json`

这是“原生生产过程录像”。

它记录原生 FreeCADCmd 中 ElementMap、StringHasher/SID、mapper、TopoShape、Sketch、PartDesign 和 Body Tip 等 producer 的顺序事件、嵌套 scope、checkpoint 与前后 snapshot。

trace 用来找 first divergence：先确认最早不同的 producer scope，再修 CAD Core 的同构模块。它不是 public 标准答案，不进入 CAD Core 请求、response、`topoNamingState` 或 shape 构造。

CAD Core 不需要按 event 序号复刻日志，也不能读取 trace 回填结果。真正需要对齐的是 trace 所揭示的生产语义、拒绝原因、映射关系和状态闭包。

### `cad-core-res/<case>.cad-core.json`

这是“CAD Core 的答卷”。

它记录当前 CAD Core 对同一 fixture 的执行结果。它可能还包含 CAD Core 产品协议需要的额外字段，例如：

- `mesh`
- 前端传输元数据
- `binaryPayloads`
- `documentObjectUpdates`

`.cad-core.json` 是 CAD Core 面向产品端的完整响应，允许比 `.freecad.json` 多出这些字段。**多出字段本身不影响正确性，也不能仅据此判定 CAD Core 答错。** 正确性比较针对双方共有的公共语义投影；CAD Core 独有字段另按其产品协议检查。

`mappedName` 也按语义比较，而不是按原始字符串比较：

- `mappedName.raw` 保留各自产生端的原始 token。FreeCADCmd 与 CAD Core 的 raw 值可能不一致，这种差异本身不影响正确性；对应条目是否一致由 `mappedName.canonical` 判定。
- `mappedName.canonical` 是 expected / diff 的稳定比较值，FreeCADCmd 与 CAD Core 的 canonical 值必须一致。canonical 不一致属于拓扑命名语义差异，不能用“raw 允许不同”或“CAD Core 多字段”放行。

因此，不能直接对 `.freecad.json` 与 `.cad-core.json` 两份原始 JSON 做全量逐字段相等判断。

所以比较时有三种判定结果：

- exact parity：投影到公共协议并完成规范化后完全一致；不要求两份原始 JSON 字节相等。
- semantic parity：公共语义一致，但存在允许的表现差异，例如额外 `mesh` 或不同的 `mappedName.raw`；其中 `mappedName.canonical` 仍必须一致。
- red：共有字段存在真正的几何、拓扑或引用语义差异，或者 `mappedName.canonical` 不一致。

### 四种校验也不能混淆

- `validate_freecad_expected_ledger.py`

  只检查“标准答案和取证材料能否互相证明”。它不读取 `cad-core-res`。

- `collect_freecad_expected.py --check`

  重新运行默认 producer-enabled FreeCADCmd，比较 public/ledger，并验证已入库 producer trace 的结构闭包。它不把 trace 纳入 public semantic diff。

- `compare_freecad_expected.py --actual-source snapshot`

  比较 checked-in 的 `.freecad.json` 和 `.cad-core.json`。它能发现快照差异，但不能证明 `.cad-core.json` 来自当前 binary。

- `compare_freecad_expected.py --live` / release gate

  真正运行当前 CAD Core，再和 `.freecad.json` 比较。这才能证明当前程序仍然对齐。

一句话概括：

> `.freecad.json` 决定“正确答案是什么”；ledger 证明“答案可信”；producer trace 解释“原生是怎样做出来的”；`.cad-core.json` 表示“CAD Core 实际答了什么”。trace 闭包也不等于 CAD Core 已答对。
