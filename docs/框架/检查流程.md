# Fixture 输入输出约定检查流程

## 1. 目的

本流程用于判断某一个 `cad-core/fixtures/<phase>/` 是否满足《输入输出约定》：

```text
输入 fixture
   ├── FreeCADCmd ──> *.freecad.json
   │                    ├── *.freecad.ledger.json
   │                    └── *.freecad.producer-trace.json
   └── CAD Core  ──> *.cad-core.json

检查 A：freecad.json <──> ledger.json
检查 B：freecad.json <──> 当前 CAD Core live output
检查 C：producer trace 的 transaction/scope/checkpoint 闭包与 first divergence
```

默认只检查用户指定的单个 phase。不得省略 `--phase` 后顺手扩大为全量运行。

## 2. 三类 fixture 必须分开裁决

`fixture_roles.v1.json` 是 fixture 角色的唯一机器来源。

| role | native release gate | 可以宣称满足的条件 |
| --- | --- | --- |
| `native` | 纳入 | catalog 有效、strict ledger 通过、live semantic green、release gate 通过且 current fresh。 |
| `protocol_only` | 不纳入 | 必须有 `.expeted.json` 和读取真实 CAD Core 输出的 focused contract test；只能宣称协议合同成立，不能宣称 FreeCAD native parity。 |
| `unsupported` | 不纳入 | 只能说明已明确排除，不能计作“满足输入输出约定”。 |

一个 phase 的 native gate 通过，不代表其中的 `protocol_only` 或 `unsupported` case 也通过。

检查 C 是按需启用的 producer 实现诊断，不进入 public release verdict。默认先完成检查 A/B；只有 A/B 暴露出无法解释或无法对齐的 public/ledger 差异，或者任务明确要求内部过程审计时，才执行检查 C。它不能替代检查 A/B，缺 trace 也不能伪装成 CAD Core public parity red。

一致性评价只汇总检查 A/B：public 行为一致并且 ledger 可验证时，直接结论为“public/ledger 一致”，不要求检查 C 提供额外证明。若因定位问题而执行了检查 C，其 producer semantic differences 必须另列为参考性 trace diagnostic，不进入 public/ledger differences，不得成为一致性 `firstFailure`。

### 2.1 内部语义 probe：不进入 native

有一类输入不是 FreeCAD 的公开 `DocumentObject graph`，而是 CAD Core 为验证抽取语义准备的内部 probe。识别特征包括：

- 根对象 `TypeId` 形如 `CadCore::...Probe`（例如 `CadCore::C3M1TopologyProbe`）；
- 由 `cad-core-*probe` 专用可执行文件或 focused test 直接消费，而不是由主 `cad-core recompute` 和 FreeCADCmd collector 共同消费；
- 输出主要是 `NamedShape`、`ElementMap`、`MapperHistory`、`ShapeFix` 等低层账本/结果，而不是公共 `results`、`topoNamingState` 和产品 response。

这类 probe 测的是“CAD Core 是否按 FreeCAD 的低层调用语义实现”，不是“FreeCADCmd 能否接受这个自定义根对象并产生 native expected”。FreeCAD 源码可能确实存在对应的 `TopoShape`、`MapperHistory` 或 `ShapeFix` 能力，但 FreeCAD 本身没有 `CadCore::C3M1TopologyProbe` 这个公开文档对象；collector 报 `TypeId ... is not enabled` 是预期边界，不表示 FreeCAD 缺少该低层能力。

因此，内部 probe：

1. 不进入 native 分母、native release gate 或“unsupported 必须转 native”的 backlog；
2. 不得为了清零 unsupported 数量而伪造 `.freecad.json` / `.freecad.ledger.json`，也不得只改 `TypeId` 将其冒充原生 fixture；
3. 必须用专用 probe binary、focused tests 和 FreeCAD 源码依据闭环验证；这证明的是内部语义对齐，不是 FreeCAD public parity。

当前角色清单只有 `native`、`protocol_only`、`unsupported` 三种机器角色，所以“probe-only”作为检查流程中的永久概念分类记录：保留明确的 `unsupported`/内部 probe 原因，并在报告中从 native backlog 永久排除。

FreeCAD2 的 producer recorder 只是观察原生执行，不会把 `CadCore::...Probe` 变成 FreeCAD public-root 类型。不得为了纳入 native 而给 FreeCAD 增加这些自定义对象或改写 probe 输入。

## 3. 固定检查基线

先进入 CAD Core 目录并显式指定 phase：

```bash
cd /Users/li/Chili3DProject/FreeCAD/cad-core
PHASE=c3m1
```

记录源码、比较器和 binary 基线：

```bash
git -C .. rev-parse HEAD
git -C .. status --short
shasum -a 256 build/cad-core
```

如果以下文件存在未提交改动，本轮结论只能标为“working-tree diagnostic”，不能直接当作已发布门禁结论：

```text
tools/compare_freecad_expected.py
tools/freecad_expected_parity/
tools/validate_freecad_expected_ledger.py
```

报告中还要保留 `runEvidence.comparisonProfileSha256`、`fixtureRolesSha256` 和 `binarySha256`，以便之后复现同一判定口径。

若 CAD Core C++ 源码比 `build/cad-core` 新，应先按任务授权完成一次相关 target 构建；不得用旧 binary 给当前源码下结论。

## 4. 步骤一：检查 role 与 artifact 结构

先查看该 phase 的角色分布：

```bash
jq --arg phase "$PHASE" '
  [.roles[] | select(.phase == $phase)]
  | group_by(.role)
  | map({role: .[0].role, cases: length})
' tools/freecad_expected_parity/fixture_roles.v1.json
```

后续 comparator preflight 必须满足：

- input 全部有 role；
- role 没有重复或缺失 input；
- native case 同时有 input、`.freecad.json`、`.freecad.ledger.json` 和 checked-in `.cad-core.json`；
- protocol-only / unsupported 没有串入 native artifact；
- 没有 orphan 或错角色 artifact；
- 至少选中一个 native case；如果所选 phase/case 只有 protocol-only、unsupported 或永久内部 probe，则比较结果为 `not_applicable`，不启动 native gate。

文件齐全只代表 corpus 结构成立，不代表 CAD Core 已答对。

若本轮还要做 producer 对齐，已选 case 另须有 `.freecad.producer-trace.json`。这个要求属于 trace migration / implementation lane，不改变现行 release-gate catalog 的 public/ledger pair 规则。

## 5. 步骤二：检查 A——验证 FreeCAD expected 与 ledger

```bash
python3 tools/validate_freecad_expected_ledger.py \
  --phase "$PHASE" \
  --strict
```

通过条件：

- 命令退出码为 0；
- 每个 native expected 都显示 `OK`；
- validated 数量与该 phase 的 native case 数一致。

这一步只证明 checked-in `.freecad.json` 的 input hash、expected hash、FreeCADCmd provenance、公开投影、引用覆盖及 round-trip / rejection evidence 闭合。它不会运行 CAD Core，也不会重新采集 FreeCADCmd。

任一 ledger 失败时，结论是“标准答案不可用于裁决”，不是 CAD Core parity red；应先修 collector 或重新成对采集 expected + ledger。

### 5.1 检查 C——验证 producer trace

本步骤不是每次一致性评价的必跑项。仅在检查 A/B 未对齐且需要定位内部原因，或任务明确指定 producer 对齐时执行；否则报告为 `not_evaluated`。

对已迁移 case 运行 native replay：

```bash
cd /Users/li/Chili3DProject/FreeCAD
python3 cad-core/tools/collect_freecad_expected.py \
  cad-core/fixtures/c4m6/topo-state-body-tip-stable-recovery.json \
  --check \
  --validate-ledger
```

collector 默认使用 `/Users/li/Chili3DProject/FreeCAD2/build/relwithdebinfo/bin/FreeCADCmd`。该检查会比较 public/ledger，并验证已有 trace 的 schema、event sequence、snapshot 引用和 scope 闭包。

当前 corpus 的 480 个 native fixture 均已有 public、ledger 和通过闭包校验的 producer trace。缺失或 invalid trace 应 hard fail 检查 C；producer semantic `different` 应保留完整首差证据并令检查 C 为 different。两者都不能改写检查 A/B 的 public/ledger 结论，也不能进入检查 A/B 的 `firstFailure`。

request-level preflight rejection 通过原生 Document recorder 的 documentless checkpoint 发布稳定 reason，并以 cancel transaction 闭合；raw `Part::GeometryCurve` helper 同样发布 documentless raw-shape checkpoint。两者都不是伪造空事件文件。

## 6. 步骤三：检查 checked-in snapshot

```bash
SNAPSHOT_REPORT="out/freecad-expected-parity/${PHASE}-snapshot.json"

python3 tools/compare_freecad_expected.py \
  --phase "$PHASE" \
  --strict \
  --actual-source snapshot \
  --output "$SNAPSHOT_REPORT"
```

snapshot 用于发现 checked-in `.freecad.json` 与 `.cad-core.json` 的差异，不能证明 `.cad-core.json` 来自当前 binary。即使 snapshot semantic green，`releaseStatus` 仍应是 `not_evaluated`。

注意：`--strict` 的 valid red 可返回 0，不能只看 shell 退出码；必须读取 report 的 `exactStatus`、`semanticStatus` 和每个 case 的 diffs。

## 7. 步骤四：检查 B——运行当前 CAD Core live release gate

纯检查时不要先运行 `--write-current`，否则会覆盖“快照是否陈旧”的证据。

```bash
LIVE_REPORT="out/freecad-expected-parity/${PHASE}-live.json"

python3 tools/compare_freecad_expected.py \
  --phase "$PHASE" \
  --release-gate \
  --output "$LIVE_REPORT"
```

live gate 必须使用当前 `build/cad-core` 对每个 native fixture 重新执行一次 recompute，并使用同一份 actual payload 完成：

1. 与 `.freecad.json` 的公共语义比较；
2. divergence / product contract 审计；
3. 与 checked-in `.cad-core.json` 的 freshness 比较；
4. strict ledger 与 role preflight。

`--release-gate` 返回非零时，phase 不通过；但仍要读取报告区分 `red` 和 `invalid`：

- `red`：当前 binary 的公共语义确实未对齐；
- `invalid`：runner、ledger、role、registry、JSON 或 current freshness 失败，当前运行不能给出通过结论；
- `green`：exact parity；
- `protocol_divergence`：exact red，但剩余差异全部是经过批准且 consumer contract 成立的表现差异。

## 8. 步骤五：定位到每个 case

输出 case 状态、freshness 和未接受差异数量：

```bash
jq -r '
  .cases[]
  | ([.diffs[]? | select(.accepted != true)] | length) as $unaccepted
  | [
      .case,
      .status,
      (if .artifactEvidence.currentFresh == null
       then "null"
       else (.artifactEvidence.currentFresh | tostring)
       end),
      $unaccepted
    ]
  | @tsv
' "$LIVE_REPORT"
```

汇总未接受差异的 decision：

```bash
jq -r '
  [.cases[].diffs[]? | select(.accepted != true) | .decision]
  | group_by(.)
  | map({decision: .[0], count: length})
  | sort_by(-.count)[]
  | [.decision, .count]
  | @tsv
' "$LIVE_REPORT"
```

定位时优先区分：

- geometry / bbox / topology count 差异；
- result publication 差异；
- subshape identity、`mappedName.canonical`、stable reference 差异；
- `topoNamingState`、ElementMap、child maps、MapperHistory 差异；
- diagnostics / rejection 边界差异；
- 仅 CAD Core 产品端拥有的额外字段。

不得把 `mappedName.canonical`、stable identity、引用恢复或 MapperHistory 的真实差异当作 raw token / 产品额外字段放行。

## 9. 最终判定规则

### native phase 满足

必须同时满足：

```text
catalog / preflight valid
AND strict ledger 全部通过
AND semanticStatus == green
AND releaseStatus in {green, protocol_divergence}
AND releaseGatePassed == true
AND 每个 native case 的 currentFresh == true
```

`exactStatus == red` 可以与 semantic parity 同时存在，但只能来自已批准的表现差异；不能存在未接受的公共语义差异。

producer trace 的 semantic status 不出现在上述 AND 条件中。默认不评估 trace；若因 public/ledger red 定位或专项内部审计而评估，它无论是 equal、projected 还是 different，都只能单独报告，不能拒绝已经满足这些条件的 public/ledger 一致性评价。

### native phase 不满足

出现任一情况即不满足：

- `semanticStatus == red`；
- `releaseStatus == red`；
- 任一 case 存在未接受的公共语义差异；
- geometry、拓扑、canonical identity 或引用语义与 FreeCAD expected 不一致。

### 无法裁决

以下情况应写“无法裁决 / invalid”，不要误写成 parity red 或 green：

- role/catalog 不合法；
- expected / ledger 缺失或 strict ledger 失败；
- 当前 binary 缺失、陈旧或 runner 失败；
- current snapshot stale；
- comparator / registry 配置无效；
- 选中的 phase/case 没有 native case，且也没有可确认的 skipped role（例如 phase/case 不存在或选择错误）。如果只是该范围没有 `.freecad.json`，应标为 `not_applicable`，不能误报为 invalid。

## 10. protocol-only 与 unsupported 收口

对 `protocol_only` case，另行确认：

1. `.expeted.json` 是明确的协议合同，而不只是 oracle blocked 说明；
2. focused test 读取真实 CAD Core 输出并断言该合同；
3. focused test 当前通过。

缺少上述任一项，只能写“protocol contract 未闭合”，不能借 native phase gate 放行。

对 `unsupported` case，只记录 role 中的 `reason`、`authority`、`nextAction` 和 `closeCondition`。它们不进入 native gate，也不计入“满足数量”。

若 `reason` 表明这是内部语义 probe（例如 `CadCore::C3M1TopologyProbe`），还要记录“probe 专项测试通过/失败”及其 FreeCAD 源码依据；该 case 从 native backlog 单列排除，不得把 collector 拒绝当成 native 缺口。

## 11. 报告模板

```text
检查范围：<phase>
基线：HEAD=<sha>，binary=<sha256>，comparisonProfile=<sha256>，roles=<sha256>
角色：native=<n>，protocol_only=<n>，unsupported=<n>；内部 probe=<n>（不进入 native 分母）
检查 A：pass / fail，validated=<n>
检查 C：not_evaluated / equal / projected / different / missing / invalid / not_applicable，trace=<case/path>；仅作按需参考的 producer diagnostic
snapshot：exact=<...>，semantic=<...>，仅作诊断
live：exact=<...>，semantic=<...>，release=<...>，gatePassed=<true|false>
freshness：fresh=<n>，stale=<n>
未接受差异：<n>，主要 decision=<...>
protocol-only focused contracts：pass / gap / none
public/ledger 一致性结论：满足 / 不满足 / 无法裁决
producer trace 诊断结论：equal / projected / different / missing / invalid / not_applicable
```

若已按需评估的 producer trace 为 `different` 而 public/ledger 一致性为“满足”，最终报告同时保留这两个结论；未评估时写 `not_evaluated`。不得把 trace difference 合并进“未接受公共差异”或一致性 `firstFailure`。

## 12. `c3m1` 判定示例

`c3m1` 的 strict ledger 全部通过，只能说明检查 A 成立。其 live gate 为 semantic red / release red，且三个 native case 都存在未接受的 geometry、subshape identity 或 topo-state 差异，因此检查 B 失败，最终结论是“不满足”。

即使三个 case 的 `currentFresh=true`，也只说明 checked-in current 与当前 binary 一致，不能把真实语义差异解释成快照陈旧。

另外，`c3m1` 中根对象为 `CadCore::C3M1TopologyProbe` 的 9 个输入永久不进入 native。FreeCAD2 recorder 可提供原生 producer 证据，但不会注册这些自定义 `TypeId`；仍应使用 `cad-core-c3m1-topology-probe` 和 `test_p6_topology.py` 验证抽取语义。
