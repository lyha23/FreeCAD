# CAD Core 反幻想审计判断标准

本文用于 review `cad-core` 实现是否真的来自本地 FreeCAD 源码，而不是按 fixture 结果或主观推断拼出来。审计结论不靠“实现看起来合理”，只看可追溯证据链。

## 核心判断标准

### 1. FreeCAD 源码锚点

每个承载 FreeCAD 业务语义的实现点，都必须能追到具体 FreeCAD 源码：

- 绝对路径：例如 `/Users/admin/Chili3DProject/重构Chili/FreeCAD/src/Mod/Sketcher/App/SketchObject.cpp`
- 类 / 函数：例如 `SketchObject::buildInternals()`
- 关键字段、枚举、调用或短句：例如 `FaceMakerBuildFace`、`WireJoiner::getOpenWires()`、`ElementMap`
- 调用顺序：谁先构造 raw shape，谁生成 `InternalShape`，谁消费 maker history

只写“参考 FreeCAD”“对齐 FreeCAD 逻辑”不合格。

### 2. cad-core 落点清楚

FreeCAD 语义必须落到正确分层：

| FreeCAD 语义 | cad-core 落点 |
| --- | --- |
| DocumentObject / Property / Link | `document/` |
| recompute 依赖与目标顺序 | `graph/` / `runtime/` |
| Sketch / Pad / Pocket / Body / Hole 等业务顺序 | `features/` |
| OCCT 构造、FaceMaker、WireJoiner、ShapeFix | `geometry/` |
| NamedShape、ElementMap、MapperHistory、stable subname | `topo/` |
| CLI / C ABI / Web / Worker 协议转换 | `adapters/` |

如果 FreeCAD 依赖 history / mapper / ledger，不能在 executor、adapter 或输出 JSON 里靠后处理修补替代。

### 3. fixture expected 来源可信

fixture 只能作为验收证据，不能作为业务逻辑来源。expected 来源按可信度分级：

| 级别 | 来源 | 判断 |
| --- | --- | --- |
| A | `FreeCADCmd` 对本地 FreeCAD 源码采集的 oracle | 可作为 parity golden |
| B | 明确标注的 geometry-equivalent FreeCAD/OCCT reference | 可用于几何等价验收，但不能证明完整命名语义 |
| C | `known_gap` / 明确不支持诊断 | 可接受，说明未伪装完成 |
| D | 从当前 `cad-core` 输出回填 expected | 不合格，除非明确标为临时 reference 且不声称 FreeCAD parity |

review 时必须检查 expected 文件或测试说明是否标明采集方式、FreeCAD 依据和已知差异。

### 4. 未实现能力必须显式暴露

未迁移的 FreeCAD 语义必须通过 diagnostics 或 `known_gap` 暴露，不能静默成功。

合格例子：

- `known_gap:taper_history`
- `unsupported_property`
- `unsupported_geometry`
- `unsupported_stable_subname`
- `split_stable_subname`
- `solve=not_migrated`

危险信号：

- fixture 通过，但没有 FreeCAD 源码锚点
- 没有 mapper/history 却声称 stable subname 已完整支持
- open wire、split fragment、InternalEdge 映射靠几何排序或 source index 猜
- adapter 层修改输出以“修正”业务语义

### 5. 测试通过不等于 FreeCAD parity

`cmake --build build` 和 Python tests 只能证明当前实现、fixture、diagnostics 自洽。是否真正对齐 FreeCAD，还要看：

- FreeCAD 源码调用链是否完整
- cad-core 是否有等价数据结构或状态机
- fixture expected 是否来自 FreeCAD oracle
- known gap 是否诚实暴露
- 命名、history、LinkSub、Placement 是否覆盖到后续引用场景

## 反幻想审计流程

### 1. 选定审计范围

每次只审一个功能族，避免泛泛而谈。推荐优先级：

1. P5 Sketch 内部面：`FaceMakerBuildFace` / `WireJoiner` / `InternalShape`
2. P6 TopoNaming：`NamedShape` / `ElementMap` / `MapperHistory`
3. P7 PartDesign：Refine / DressUp / transformed family ownership
4. P8 Link / Assembly：LinkSub、ShowElement、cross-document、Joint / solver

### 2. 建立证据链表

每个语义点按以下表格审计：

| 审计项 | FreeCAD 依据 | cad-core 实现 | fixture / oracle | 当前结论 | 风险 |
| --- | --- | --- | --- | --- | --- |
| 语义点名称 | 源文件、函数、关键字段、调用顺序 | 文件、函数、数据结构 | fixture 名、expected 来源、诊断码 | 通过 / 子集 / known gap / 不合格 | 缺失 history、fixture 特判、命名漂移等 |

结论口径：

- `通过`：FreeCAD 源码依据、cad-core 落点、fixture/oracle 三者闭合。
- `子集`：实现是 FreeCAD 语义的受限子集，边界和 diagnostics 清楚。
- `known gap`：明确未完成，输出不伪装成功。
- `不合格`：缺源码依据、从 fixture 倒推、输出端修补、或没有显式 diagnostics。

### 3. 检查源码注释

新增或承载 FreeCAD 语义的结构体、函数、枚举、字段、executor 主路径，旁边应有 FreeCAD 依据注释。最低要求：

```cpp
// FreeCAD: /Users/admin/Chili3DProject/重构Chili/FreeCAD/src/Mod/PartDesign/App/FeaturePad.cpp::Pad::execute(),
// calls "buildExtrusion(ExtrudeOption::MakeFace | ExtrudeOption::MakeFuse)".
```

普通 helper、测试辅助、小型 JSON 转换不强制，但只要承担业务语义，就必须可追溯。

### 4. 检查反模式

发现以下模式时，应暂停继续叠规则，回到 FreeCAD 源码账本：

- 按 fixture 名称、几何类型组合、edge 顺序、split 顺序写分支
- 在 `sketch_object.cpp` 中猜测 open wire 归属
- 在 adapter 或导出层修剪 subshape / stable subname
- 用当前输出生成 expected，再反过来证明实现正确
- 只验证 face/edge 数量，不验证 `ElementMap` / history / stable subname
- FreeCAD 有内部状态机，但 cad-core 没有等价结构却声称完整支持

### 5. 形成审计结论

审计报告只保留对判断有用的信息：

- 当前基线
- FreeCAD 调用链
- cad-core 对应落点
- 已通过的 oracle / fixture
- 已知差异和风险
- 下一步必须补的源码账本或验证项

不要写流水账式过程日志。

## P5 / P6 首轮审计建议

建议先审 P5 Sketch 内部面与 P6 TopoNaming，因为这两块最容易出现“几何结果看起来对，但 FreeCAD 账本没有迁移”的问题。

首轮审计问题：

1. `SketchObject::buildInternals()` 的 FreeCAD 调用链是否完整落到 `cad-core`？
2. `FaceMakerBuildFace` 是否只是 closed-wire face-with-holes 子集，还是已迁移 split/intersection history？
3. `WireJoiner::getOpenWires()` 是否有等价 `EdgeInfo` / `WireInfo` / `iteration` / `openWireCompound` 状态机？
4. `InternalEdgeN` / `InternalVertexN` 是否由 history / element map 生成，而不是几何相等或顺序猜测？
5. stable subname 恢复是否走 `NamedShape` / `ElementMap` / MapperHistory，而不是输出端 retag？
6. 对未完成路径是否有明确 `known_gap` 或 diagnostics？

只有这些问题能闭合，才能说实现是 FreeCAD 迁移；否则只能说是当前 CAD Core 的局部几何子集。
