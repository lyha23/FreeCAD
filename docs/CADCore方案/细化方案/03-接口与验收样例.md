# 接口与验收样例

本文件固定 CAD Core 的输入、输出、fixture 和 diagnostics 口径。它不是实现日志；新增能力只在这里补充验收分层和稳定错误码。

## CLI

```bash
cd /Users/li/Chili3DProject/重构Chili/FreeCAD/cad-core
./cad-core recompute fixtures/mvp/rect-pad.json --output out/rect-pad.result.json
```

输入是完整 `DocumentObject graph`，不是局部操作命令。`recompute.objs` 只表示本次计算目标。

CLI 可选把本次 recompute 已计算出的对象写成文件：

```bash
./cad-core recompute fixtures/p8/part-box.json \
  --output out/part-box.result.json \
  --export-object Box \
  --export-format brep \
  --export-file out/part-box.brep
```

当前导出格式为 `brep` / `step` / `stl`，`stl` 可额外传 `--stl-deflection`。导出使用本次请求内的 `TopoDS_Shape`，是 CLI adapter 的文件副作用；BREP / STEP / STL 内容不进入 `DocumentObject graph` 或默认 JSON 状态。

## C ABI

`cad_core_ffi` 是薄 adapter。它应和 CLI 调用同一个 core recompute 入口，返回同一类 JSON 结果和 diagnostics。C ABI 不直接解析 FreeCAD 业务属性，不保存 shape，也不补拓扑命名。`cad_core_capabilities_json()` 的 `topo_history` 会声明当前 stable subname resolution、maker history、terminal history 和 `element_history_status` 子集，同时发布 `part_workbench.sweep` 的 source-backed `Part::Sweep` / PipeShell first batch、`part_workbench.filling` 的 source-backed `Part::FilledFace` helper first batch、`part_workbench.geomplate` 的 source-backed `Part::GeomPlateSurface` geometry helper first batch，以及 `pipeshell` / `filling` maker-history producer；完整 MapperHistory、FaceMaker / WireJoiner history 和导入 shape ElementMap 等 gap 仍按各自阶段边界维护。Sweep 发布不包含 `Linearize=true` post-processing、advanced PipeShell wrapper、auxiliary spine、located profile、support、trihedron/binormal 或 Hole `ModelThread` 内部 PipeShell；Filling 发布不包含原生 FreeCAD `Part::FilledFace` DocumentObject、`surface` / `supports` / `orders`、constraints、non-default params、compound optional case 或完整 surface family；GeomPlate 发布不包含 GUI / fake `Part::GeomPlate` DocumentObject、initial surface、G1 curve-on-surface、projected 2D curve、custom criteria、`Part.PlateSurface(Curves=...)` 或完整 surface family。

## 输入规范

```json
{
  "Objects": [
    {
      "Name": "Pad",
      "ID": 2,
      "TypeId": "PartDesign::Pad",
      "Properties": {
        "Profile": {
          "PropertyType": "App::PropertyLinkSub",
          "value": "Sketch",
          "SubList": []
        },
        "Type": "Length",
        "Length": 10
      }
    }
  ],
  "recompute": {
    "objs": ["Pad"]
  },
  "topoNamingState": {
    "schemaVersion": "cad-core.topo-state.v1",
    "objects": {}
  }
}
```

规则：

- `Objects[]` 中的 `Name` 是运行时引用 key。
- `TypeId` 决定 executor。
- `Properties` 沿用 FreeCAD 属性名。
- dependency-bearing 的 `PropertyLink*`、`PropertyXLink*` 和 `PropertyLinkGlobal` 归一为 dependency edge；`Property*Hidden` / `PropertyXLinkSubHidden` 可被 executor 读取，但不生成 graph dependency。
- `topoNamingState` 是可选输入，调用方应把上一次响应中的完整快照原样带回。CAD Core 服务端不保存 session；旧 state 只用于 `StableSubList` / `ShadowSub` / `ReferenceShadow` 恢复、split / deleted / ambiguous 判断和引用更新建议，不参与 shape 构造。
- `StableSubList` / `FullSubList` 可与 `SubList` 并存，用于 topo naming 引用恢复；`StableSubList` 中的 FreeCAD mapped-name token 只有在配套 `topoNamingState` 证据存在并校验通过时才可作为跨请求引用恢复输入。`ReferenceShadow` 校验普通 Shape LinkSub 时也会先消费 `StableSubList -> topoNamingState / ElementMap -> current subname`；`elementReferenceUpdates` 会保留显式 `FullSubList`，避免旧引用恢复后丢失完整 subname 证据。
- C ABI `document.link_property_shapes` 必须暴露 parser 已支持的 `PropertyLink*` / `PropertyXLink*` 输入 shape，尤其是 `PropertyXLink` / `PropertyXLinkSub` / `PropertyXLinkSubList` / `PropertyXLinkList`；`PropertyXLinkList` 同时接受 object-only `values` 和 sub-element `SubSet`，避免 Web adapter 只靠隐式兼容。

## 输出规范

结果至少包含：

```text
objects
mesh
subshapes
named_shapes
topoNamingState
elementReferenceUpdates
documentObjectUpdates
diagnostics
```

`topoNamingState` 是本次 recompute 后的新完整拓扑命名快照，调用方下次请求应原样带回。`elementReferenceUpdates` 是本次请求内 stable subname / shadow recovery 的引用更新建议；当旧 `SubList` 依赖 `StableSubList` 才能定位当前元素时，更新建议会返回新的 `SubList`、`StableSubList`、`ShadowSub` 和刷新后的 `ReferenceShadow` fingerprint。`documentObjectUpdates` 是本次请求内的对象图更新建议，当前用于 Link 生命周期同步：`ShowElement=true` LinkElement 的 create / claim / update / delete，`ShowElement=true` 显式 ElementList 的 owner `ElementCount` / `VisibilityList` sync 与 child `_LinkOwner` / `LinkedObject` / `LinkTransform` sync，其中 `CopyOnChangeOwned` child 不覆盖自有 `LinkedObject`，`ShowElement` true->false 时 child placement / scale 收回到 owner list 并删除 owned child，以及 `ShowElement=false` ElementCount owner `PlacementList` / `ScaleList` / `VisibilityList` resize sync。前端可据此更新 `DocumentObject graph` 和 `topoNamingState`；CAD Core 不在后端持久化或隐式改写请求 graph。

## topoNamingState 协议状态

`topoNamingState` 采用客户端携带快照模式：服务端物理上仍无 session，调用方负责保存上一次响应并在下一次请求中带回。该字段的详细契约见 `docs/接口规定/7-8-11-08-topoNamingState客户端携带状态接口方案.md`。

最小结构：

```json
{
  "schemaVersion": "cad-core.topo-state.v1",
  "producer": {
    "cadCoreVersion": "",
    "freecadVersion": "",
    "occtVersion": ""
  },
  "documentHash": "",
  "objects": {
    "BooleanFragments": {
      "objectHash": "",
      "elementMapVersion": "",
      "subshapes": {
        "Face1": {
          "subname": "Face1",
          "rawFreecadMappedName": "Face1;:H551,F;CSD;:H551:4,F;:H,F;:H:5,F",
          "canonicalFreecadMappedName": "Face1;:H*,F;CSD;:H*:*,F;:H,F;:H:5,F",
          "resolvedIndexed": "Face1"
        }
      },
      "elementMap": {},
      "childElementMaps": [],
      "mapperHistory": []
    }
  }
}
```

规则：

- `topoNamingState` 不能作为几何建模输入；shape、bbox、mesh 和 volume 只能由当前 `DocumentObject graph` 计算。
- `rawFreecadMappedName` 是旧账本证据；没有配套 state 时，不得把裸 token 当作长期 stable subname。
- `canonicalFreecadMappedName` 只用于 expected / diff 稳定比较，不是 FreeCAD 原生可解析输入。
- 旧 state 的 `schemaVersion`、producer 版本、`documentHash` 或 `objectHash` 不匹配时，必须降级为不可恢复或 evidence-only，并返回结构化 diagnostic。
- 响应必须返回新的完整 `topoNamingState`，不能只返回增量；前端以下一次响应替换本地旧快照。

diagnostics 字段口径：

```text
level
code
message
object
property
stage
target
subname
```

常用错误码：

```text
parse_error
missing_target
missing_link_target
cycle_dependency
unsupported_type
unsupported_property
unsupported_geometry
unsupported_subshape_kind
invalid_property_type
invalid_link_value
invalid_placement
invalid_subshape
invalid_length
invalid_angle
open_profile
execution_failed
unsupported_stable_subname
split_stable_subname
deleted_stable_subname
```

## 验收规则

- 正常 fixture diagnostics 必须为空。
- 错误 fixture 的 diagnostics code 必须稳定。
- 几何 fixture 优先校验 bbox、volume、topology count、subshape / named shape 语义。
- FreeCAD oracle 不可用时，必须在 fixture 或测试名中明确 known gap。
- 文档、fixture 和 tests 必须同步更新。

### `expected/*.freecad.json` 口径

- `fixtures/<phase>/expected/*.freecad.json` 是成功几何 fixture 的 FreeCAD / oracle golden，不是每个输入 fixture 的一对一索引。
- 错误 fixture 只固定 `diagnostics.code`，不要为了凑数量新增空 `expected` 文件。
- 对 bbox、volume、topology count、mesh summary、named shape 语义做断言的成功几何 fixture，应优先使用同名 expected 文件，避免把几何预期分散硬编码在 Python 测试里。
- expected 文件优先包含 `object`、`reference`、`freecad_version`、`bbox`、`volume`、`topology_counts`；确有需要时再补 `mesh_summary`、`named_shapes` 或 stable subname 相关字段。
- stable subname 相关 expected 中，`rawFreecadMappedName` 保留 FreeCAD 原始账本 token，`canonicalFreecadMappedName` 只用于比较稳定性，`stableSubname` 只有在配套 state / ElementMap 证据可恢复时才可声明为长期引用输入。
- native expected 的 `bbox` 默认按 CAD Core 输出契约验收，即 FreeCAD `optimalBoundingBox()` / OCCT `AddOptimal` 的 tighter bbox，而不是 FreeCAD UI/display 用的松 `Shape.BoundBox`；若导入 shape 或 section edge 在不同 OCCT runtime 下保留 tolerance 外扩，保留 FreeCAD bbox 作为 oracle，并用显式 `bbox_delta` 标明容差边界。
- 老 fixture 如果已经存在内联几何断言，也必须迁移成 expected 文件；迁移规则见 `docs/5-30-04-33-CADCore-fixture-expected迁移方案.md`。
- 如果 FreeCAD oracle 暂不可用，只能写清楚 geometry-equivalent `reference` 或 `known_gap`，不能把 cad-core 当前输出伪装成 FreeCAD golden。

当前 expected 覆盖基线：`mvp=1`、`p2=2`、`p3a=5`、`p3b=24`、`p4=7`、`p5=66`、`p6=16`、`p7=82`、`p8=69`、`c3m4=19`。成功几何 fixture 应由 `tests.test_expected_fixtures` 自动发现；错误 fixture 继续留在 diagnostics 矩阵。P8 FreeCADCmd collector 当前可校验 63 个 expected，剩余 skip 主要是缺失 expected 的错误 fixture，以及目标为 `App::Link` 的多层 object / label LinkSub、plain group `_ChildCache`、Link 后续 history retag 这类 source-equivalent 路径；C3M4 Sweep / Filling / GeomPlate invalid fixture 只固定 diagnostics，不伪造 shape expected。
